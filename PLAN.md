# Implementation Plan

Full build plan for the Oracle Property Intelligence Platform assignment. `README.md` is the acceptance-criteria source of truth; `ENTITY-MODEL.md` is the data-design source of truth; `CLAUDE.md` is the process/style reference. This file is the roadmap tying them together into phases.

## Constraints that shape this plan

- **Data access:** confirmed access is the public `elephant` MCP server (IPFS-published Oracle open data), plus a verified-real, publicly downloadable Parquet export of the full Lee County dataset (see resolved risk below). No credentials to the company's private `elephant-query-db` Neon instance — but its schema source is public on GitHub and can be reused directly (see Phase 2).
- **Scoring reality:** the hiring evaluator (`slowking`) treats a deployed, reachable, working runtime as an absolute gate (no exceptions) and weights functional outcome + runtime/demo quality at 60 of 100 points, vs. 5 for matching the company's internal AWS toolchain exactly. Every phase below is ordered and scoped to protect the runtime gate first.
- **Stack:** Next.js + TypeScript + tRPC + Drizzle + Neon Postgres/pgvector + Vercel AI SDK, deployed on Vercel (see `CLAUDE.md` for the full reasoning and deviations from the company's AWS-based internal conventions).
- **Database hosting:** Neon, provisioned via the Vercel Marketplace integration (auto-wires `DATABASE_URL`). Staying on Neon's free tier (verified live: 0.5 GB storage/project, 100 compute-hours/month, autoscales to zero when idle, no credit card, doesn't expire) — no Docker, no self-hosted Postgres; see reasoning in conversation. **0.5 GB is the real constraint shaping Phase 3's approach below.** Originally estimated the full skeletal backbone alone would fit in roughly half that budget — **wrong, measured live**: loading it actually hit Neon's hard storage error (`could not extend file because project size limit (512 MB) has been exceeded`) at 171,000 properties / 490MB (~2.9KB/property across the 6 backbone tables — the adopted schema's own indexes on `addresses` account for most of that). Extrapolated, all 511,695 properties would need ~1.46GB, roughly 3x the free tier. Decided (with the user) to bound the backbone too, not just the enrichment subset — see below.

Database schema: **adopted `elephant-xyz/elephant-query-db`'s real Drizzle schema** (copied per the `use-elephant-query-db` skill's documented approach into `src/server/elephant-query-db/schema/`, since `@elephant-xyz/query-db` isn't published on npm) instead of hand-rolling tables. Added three genuine extensions in `src/server/schema/extensions.ts`: `projects` (+ `project_permits` join table), `tenants`, and `public_records` (the literal "Public Records" entity `README.md` names — one row per distinct `(sourceSystem, sourceRecordKey)` pair, no FK added to any adopted table; see `ENTITY-MODEL.md`), all using the schema's own `sourceMetadataColumns()` provenance columns for consistency. Stripped the `.js` suffixes from all copied files' relative imports (mechanical, one-time). Worth knowing if the schema is ever re-synced from upstream.

### Phase 3 — Data Access & Ingestion — done at full county scale

**Update (post storage-tier upgrade):** everything below this note describes the original free-tier-constrained build and is kept as real engineering history — the numbers in it (101,156 properties, 288MB, "not literally all 511,695") are **no longer current**. Neon was upgraded to a paid (Launch) plan, which removed the 0.5GB ceiling that drove every scoping decision below. The backbone was then expanded **additively** (new `--additive-only` mode added to `backbone.ts`, using `onConflictDoNothing` instead of `onConflictDoUpdate` so it provably cannot touch a pre-existing row — verified: exactly the count of new rows showed a fresh `updated_at`, never more) to the full county:

- **Properties: 511,695 / 511,695 (100%)**, up from the original 101,156 (19.8%).
- **Permit enrichment: 26,952 properties** with real permit history (99.95% of the 26,965 county-wide that have any `has_permits` signal), via `enrich-all.ts` (concurrency tuned from 15→150 after profiling; 150 was the verified-safe ceiling against the shared production DB).
- **Tenant/occupancy: 42,124 properties** (99.3% of 42,407 with `has_sunbiz_tenant` signal).
- **BBB: 867 contractor-reputation profiles** (18 negative-rated, up from an earlier partial 15).
- **`projects` (derived renovation groupings): 99,217** property+contractor groups from **175,477 permits, 0 orphaned `project_permits` rows** — this also required fixing a real bug in `derive-projects.ts` (an `onConflictDoNothing().returning()` call was silently falling back to a freshly-generated, never-inserted UUID whenever a project already existed from an earlier run, which is what originally caused a foreign-key violation; fixed by batch-inserting then bulk-re-selecting real ids).
- DB size ~4.7GB after `npm run db:vacuum` (vacuum script itself needed fixing too — it only covered the original backbone tables, not `tenants`/`business_reputation_*`/`business_registration_*`).
- The RAG embeddings index (`entity_embeddings`) doesn't auto-refresh when ingestion adds data out of band — it went stale relative to this expansion until a secret-gated `POST /api/admin/rebuild-embeddings` endpoint (`src/server/rebuild-embeddings.ts`) was added to refresh it on demand (runs on Vercel, which already holds the AI Gateway credentials this needs, rather than requiring them locally).
- **Known, still-open limitation, unaffected by any of the above:** "projects completed by contractors with negative BBB ratings" still returns empty even at full data scale — confirmed directly against the DB (0 permits/projects resolve to any of the 18 negative-BBB `companyId`s). This is the contractor-identity-fragmentation limitation two paragraphs below, not a coverage gap — loading more data doesn't fix it, because the permit-contact-derived identity and the BBB-profile-derived identity for the same real business are resolved independently and don't converge.

**Original build (kept as history below):**

**Done:** Neon Postgres provisioned via the Vercel Marketplace integration (project `neon-gray-door`, free tier), connected to the Vercel project (auto-injects `DATABASE_URL` + related vars), and pulled locally into `.env.local` (git-ignored). `npm run db:push` ran against it — verified directly with a live query (not just trusting the CLI): all 55 tables exist, including our `projects`/`project_permits`/`tenants`/`public_records` extensions. `pgvector` 0.8.0 enabled and verified via `pg_extension`. One setup fix along the way: `drizzle.config.ts` didn't pick up `.env.local` automatically (that's a Next.js-specific behavior, not something `drizzle-kit` does on its own) — fixed with Node 22's built-in `process.loadEnvFile()`, no new dependency needed.

**Backbone load done and verified live:** 101,156 properties (parcels/addresses/properties/ownerships/sales_histories/public_records) across all 47 Lee County cities, 288MB used of the 512MB free-tier cap. See the stratified-selection writeup below for why this is 101,156 and not 511,695.

**Validated thoroughly before moving to enrichment** — not just trusted: found and fixed 2 stray property rows left over from an earlier ad hoc diagnostic run (harmless, but cleaned up so the DB exactly matches the documented 101,156 selection, confirmed via a direct id-set comparison — 0 stray rows, 0 duplicates after). Spot-checked 5 random properties directly against the source Parquet (not just the DB) — the one that was in-subset matched exactly on city/address/usage type; the other 4 correctly weren't loaded (consistent with a ~20% selection rate). Re-ran the full idempotent load a second time — row counts stayed byte-for-byte identical (no duplicates from re-running).

**Real operational gotcha found: Postgres MVCC bloat from re-running the idempotent upsert.** Re-running the (already-loaded, unchanged) backbone grew the DB from 288MB to 353MB even though the row count didn't move — every `ON CONFLICT DO UPDATE` writes a new row version rather than updating in place, and the old version becomes dead space until `VACUUM`ed. On a 512MB budget, repeatedly re-running scripts during development/testing could silently eat the remaining headroom for zero new data. Added `scripts/ingest/vacuum.ts` (`npm run db:vacuum`) — `VACUUM FULL` on all 6 backbone tables brought it down to 249MB, even lower than the original 288MB (also compacts more efficiently than the incremental inserts did). **Worth running after any bulk re-run of the ingestion scripts, not just once.**

**Permit enrichment built and verified live (`scripts/ingest/enrich.ts` + `permits.ts` + `contractor.ts` + `fetch-property.ts`):**

- Fetches each property's full consolidated JSON directly by CID over plain HTTPS (`fetch-property.ts`) — no MCP dependency, per the architecture note above.
- Loads `property_improvements` + all 5 child tables (`permit_contacts`, `permit_events`, `permit_fees`, `permit_links`, `permit_custom_fields`), keyed per-permit by `${propertyId}:${permitNumber}` (falling back to an index when `permitNumber` is missing — not guaranteed present on very old records).
- **Real data quirks found while building this, not assumed:** `improvementType` is often messy free text on legacy "Closed-Conversion" records (a scraper artifact, not our bug) — `projectDescription` is the cleaner field, so renovation-type classification (Phase 3 Project derivation, not yet built) should weight `projectDescription` over `improvementType`. The adopted schema has a separate `improvementStatus` column but Oracle's raw JSON only gives `recordStatus` — added `deriveImprovementStatus()` to classify open/closed/unknown from the raw text since "identify properties with an open permit" needs this. Permit `contacts[]` is often empty (no contractor identity available for that permit) — handled gracefully, no company/person row forced.
- **Contractor identity resolution (`contractor.ts`) — real problem found and partially solved, honestly scoped:** Oracle's raw contact strings embed phone/license/address in one unparsed blob with the dedicated columns left null (e.g. `"K. Galloway Galloway Roofing, LLC 7253 Gasparilla Rd. ... Primary Phone: 9416973737 ... CCC1328485"`). Built a regex extractor for phone/email/Florida-license-number, and address-boundary stripping. Found live that the same real contractor's "Applicant" and "Licensed Professional" contacts often list person-name and company-name in **different order** — confirmed with a real pair ("ROBERT S MILLER GRANDE AIRE SERVICES INC" vs "GRANDE AIRE SERVICES INC ROBERT S MILLER") that a naive exact-string match would treat as two different companies. Fixed with a sorted-token match key (order-independent) — verified this actually merges that pair into one `companies` row. **Known, documented, not-solved limitation:** abbreviated name variants (e.g. "K. Galloway" vs "KENNETH D GALLOWAY") still produce different token sets and won't merge — full fuzzy/NLP name matching is out of scope for this pass. Revisit only if this fragmentation turns out to visibly hurt the Contractor View.
- Verified end-to-end on a 10-property test batch: all rows landed correctly, idempotent on re-run, contractor dedup fix confirmed with a real before/after comparison (9 companies → 8 after the fix, for the same 10 properties).

**Done (see the update note at the top of this phase for real numbers):** scaling permit enrichment past the original 10-property test batch to the full county; Sunbiz enrichment; BBB enrichment; `tenants`/`projects` derivation; `public_records` populated for the derived entities.

**Resolved:** full-scale ingestion is achievable without the MCP's `queryProperties`/`getPropertyQuerySchema` tools (those only exist on `elephant-mcp`'s `main` branch, not the `v1.7.0` tag we're pinned to — confirmed by diffing `src/tools/registry.ts` on both). Instead, download Lee County's published query-table Parquet directly over plain HTTPS — `https://ipfs.filebase.io/ipns/k51qzi5uqu5djd4ohcf3qm87dhlt0e270xw8ejhkyia62edr76uj0u05hrf7m5` — re-verified live at Phase 3 start as the caution note below required (HTTP 200, `application/vnd.apache.parquet`, ~229MB, `Last-Modified` a day old — confirms the IPNS pointer really had been re-published since Phase 1/2, exactly the risk we flagged). **Caution stands:** it's a live pointer, re-verify again before any future re-run.

**Tooling gotcha found and fixed:** tried the native `duckdb` npm package first (per the original plan) — it reads Parquet via HTTP fine for small reads (`LIMIT 1` worked), but hard-crashes (silent native crash, no catchable JS error, not a timeout) on any full-table scan of this file on this Windows machine, even single-threaded (`PRAGMA threads=1`) and with 16GB+ RAM free (ruled out OOM). Not worth debugging a native Windows binary bug further — switched to `hyparquet` (pure JS, zero native dependencies, zero-config on any platform). Read and aggregated all 511,695 rows in 363ms. `duckdb` removed from `package.json`, `hyparquet` added.

**Decided scope (driven by the free-tier 0.5 GB storage cap, confirmed by actually hitting it, not just estimated):**
1. **Backbone load — a stratified 101,156-property subset, not literally all 511,695.** Explicit, deliberate scope call after the full backbone blew the storage budget 3x over (see above) — same free-tier-driven reasoning already applied to the enriched subset, just discovered to also apply here. "Load all available property records" is satisfied for a large, representative fifth of the county, not every single row; documented here plainly rather than glossed over.

   Selection isn't "first N rows" — that turned out to be geographically skewed (the Parquet is physically clustered by parcel identifier, so a naive slice landed almost entirely in one small area before this was caught). `scripts/ingest/select-subset.ts` instead: groups by city, allocates each city a share proportional to its population (with a floor so small cities aren't zeroed out), and within each city's allocation prioritizes properties with `has_permits`/`has_sunbiz_tenant`/`has_bbb_contractor` signal first. Result, verified live: **101,156 properties across all 47 cities, using 288MB (224MB headroom left), capturing 66,570 of the county's 66,685 signal-bearing properties (99.8%)** — the stratification means the backbone already contains nearly every property worth enriching, so the enriched-subset step below draws from within it rather than needing separate out-of-backbone fetches.
2. **Enriched fetch — a further bounded subset within the backbone above**, not all 66,570 signal-bearing properties in it. Call `getOracleProperty` (or fetch by `property_cid` directly, see below) for the chosen subset, load full detail into the adopted `elephant-query-db` tables. Concrete size TBD when Phase 3's enrichment step is actually built (see risk #2) — large/varied enough for every Required Demo Inquiry, small enough to leave room for `pgvector` embeddings (Phase 4) within the remaining ~224MB.

**Architecture: the ingestion script needs no MCP dependency at all, not even for the enriched fetch.** The Parquet's `property_cid` column is each property's IPFS content ID for the exact same consolidated JSON `getOracleProperty` returns — confirmed live: `https://ipfs.filebase.io/ipfs/<property_cid>` returns identical content (byte-for-byte size match) to what the MCP tool fetched for the same property earlier in this project. So the ingestion pipeline is two plain-HTTPS steps (Parquet, then per-property IPFS fetch by CID), runnable as a standalone script independent of any live Claude Code/MCP session — important for it to be re-runnable/automatable later.

**ESM/CJS interop gotcha found and fixed:** `hyparquet` is ESM-only, so `scripts/` got its own nested `package.json` with `"type": "module"`. That surfaced a second, subtler issue: importing our own `src/server/schema/index.ts` (a chain of `export * from` barrel re-exports) came back with only a single `default` key instead of the real named table exports — Node's CJS→ESM interop couldn't statically analyze the re-export chain (via `cjs-module-lexer`) and collapsed everything under `.default`. Fixed by giving `src/` its own `"type": "module"` too, so Node treats those files as real ESM directly rather than CJS-transpiling them first. Confirmed safe for the Next.js app itself, since Turbopack uses its own bundler resolution, independent of Node's runtime module type — already proven true once with the earlier `.js`-suffix fix.

**Address parsing added:** Oracle never gives granular street components (number/name/suffix) anywhere — confirmed directly against both the Parquet and the full consolidated JSON, both only carry one combined string (e.g. `"4815 SHORE LANE"`). Added `scripts/ingest/address.ts` using the `parse-address` npm library (a well-established US address parser) to split this into the adopted schema's granular columns, plus a normalized key + SHA-256 hash (Node's built-in `crypto`, no new dependency) for reliable matching later — particularly the Sunbiz-to-property address join for `Tenant` derivation. Verified against real output (`"4815 SHORE LANE"` → number `4815`, street `SHORE`, type `Ln`).

**Real-world data quirk found and fixed:** multiple properties can share one parcel (e.g. multiple units/buildings on the same parcel) — a bulk `INSERT ... ON CONFLICT` can't target the same row twice, so `parcels` rows are deduped by `parcel_identifier` within each batch before inserting, while the full batch is still used for the subsequent parcel-id lookup (since several properties may resolve to the one inserted parcel row).

Transform into the canonical schema: resolve Contractor/Business identity via the `companies`/`people` hub-table join pattern (not an invented scheme — see `ENTITY-MODEL.md`), derive Project groupings from clustered Permits, parse contractor `rawName` strings into the already-structured `permitContacts` columns, preserve provenance on every row.

Satisfies: all the "Load all available..." and "Normalize and reconcile" and "Create durable entity identifiers" and "Preserve source provenance" acceptance criteria.

## Open risks

1. ~~Bulk SQL MCP tool availability~~ — **resolved**: not needed. Full-scale data comes from the Parquet backbone (Phase 3), verified live.
2. ~~Subset size for the enriched fetch~~ — **resolved**: no longer bounded by storage after the Neon plan upgrade. Enrichment now covers all 66,685 county-wide signal-bearing properties (26,952 with permits, 42,124 with tenants, 867 BBB profiles) — see the Phase 3 update note above for real numbers.
3. **`elephant-query-db` DB access** — still don't have credentials to the live Neon instance, only its public schema source (which we're adopting). If real access becomes available later, worth re-asking, but not blocking progress.
4. ~~Provenance column location~~ — **resolved**: `shared.ts`'s `sourceMetadataColumns()` (`sourceSystem`/`sourceRecordKey`/`sourceRecordHash`/`sourceArtifactUri`/`loadedAt`) is real and spread into every table. Our new tables (`projects`, `tenants`) reuse the same helper — see `ENTITY-MODEL.md`.
5. ~~`sunbizTenants[]` fill rate appears very low~~ — **corrected**: the small-sample finding (8 live `getOracleProperty` calls, all empty) was misleading, not a real data problem. Computed the real county-wide rate directly from the Parquet's `has_sunbiz_tenant` flag (via `hyparquet`, not sampling): 42,407 of 511,695 properties (8.3%) have a populated `sunbizTenants[]`. Cross-checked the flag against a real record (parcel `02432006000180040`, Boca Grande) — `has_sunbiz_tenant: true` correctly predicted a populated array (2 distinct LLCs, 4 entries with some duplication worth deduplicating at ingest time). An 8-sample all-empty result at a true 8.3% rate has ~48% probability by chance alone — not actually surprising in hindsight. **Implication for Phase 3:** Oracle's pre-embedded array is a fine primary source for `tenants` after all (42,407 candidates is plenty for a representative subset); still worth adding our own address-based join as a supplement for properties Oracle didn't flag, but it's no longer a load-bearing requirement the way the earlier (wrong) finding implied.
6. ~~Oracle's per-record `collectedAt` timestamp isn't a typed column~~ — **resolved**: confirmed live that every raw property JSON carries a top-level `collectedAt` (e.g. `"2026-06-25T05:49:06.721Z"`) with no typed home in the adopted schema (only our own `loadedAt`). Rather than stash it in `sourcePayload` JSONB, it now has a proper column on the new `public_records` table (see risk #7 / `ENTITY-MODEL.md`'s Public Record section) — Phase 3 ingestion writes it there directly.
7. **`public_records` needs populating during ingestion, not just designed.** For every distinct `(sourceSystem, sourceRecordKey)` encountered while loading a domain row, Phase 3 must also upsert a matching `public_records` row (`documentType`, `collectedAt`, the shared provenance columns) — including one per derived `projects`/`tenants` row (`documentType: "derived_inference"`). Easy to build the tables and forget this step since it's not required by any single domain table's foreign keys.
